# RBAC / Authorization Audit (issue #81, parent #80)

Read-only audit of every `app/**/actions.ts`, `page-data.ts` loader, Route Handler and `lib/` mutation under `client/`, against `client/lib/permissions/*`, ADR 0009, ADR 0013 and `CONTEXT.md`. No code was changed. Snapshot: `main` at `d8ecd0f`. Paths are relative to `client/`.

Levels use `ListAccessLevel` (`NONE < READ < WRITE < LEAD < ADMIN`) from `lib/permissions/list-access.ts`. "WS-Admin" means Workspace Owner/Admin (`canManageWorkspace`). "Member" means any WorkspaceMember row.

Sources: ADR `docs/ADR/0009-two-tier-roles-with-list-scoped-guests.md` (resolution order, private Lists must be undiscoverable, Viewer is a hard ceiling, Guest has no visibility beyond its List), `docs/ADR/0013-chat-channels-bypass-viewer-guest-read-only-ceiling.md` (Channels are the only ceiling exception), and the code cited per row.

## Headline

The core gates are mostly right. Every Item/List/Section/Label/Custom-Field/Guest/Membership mutation under `lib/` goes through `resolveListAccess` or `resolveItemAccess` using the real List (derived from the Item/Section/Definition row, not the URL), and the Viewer/Guest ceiling holds on every write path (all Item writes need `WRITE`). The two List page loaders and the CSV export compare URL `workspaceId` to `list.workspaceId`. The gaps are in what sits around that core:

1. Nothing honors `Workspace.deletedAt` (#75, schema change is still uncommitted in the working tree and `lib/workspace/workspace-visibility.ts` does not exist yet). Every gate below needs the check, ideally once, inside `resolveListAccess` and a new workspace-access resolver.
2. Archived Lists are not read-only: no mutation checks `list.archivedAt`.
3. Private-List leakage through non-List surfaces: Assignee targets, Notifications, My Tasks/Home, cross-List Dependency titles. These read paths trust a row that was valid at write time and never re-check current access.
4. Raw role compares are duplicated in 8 places instead of one workspace-level resolver.

## Verified OK (no action)

- List mutations: `archiveList`, `restoreList`, `setListStatus`, `updateListDescription` (`list-lifecycle.ts:35-119`), `grantGuestAccess`/`revokeGuestAccess`, `addListMember`/`removeListMember` (target must be a Workspace member), custom field definitions, `toggleStarred`: all resolve the List by id and require the documented level (`LEAD`, or `READ` for starring). The Server Actions pass the URL `listId` but the lib re-derives the Workspace from the List row, so a mismatched URL `workspaceId` grants nothing.
- Section/Item-id based actions (`renameSection`, `deleteSection`, `duplicateSection`, `restoreItem`, `transitionItemState`, `moveItemToColumn`) authorize against the owning List of the row, not the URL `listId`. `addChildItemAction` is safe because `createItem` enforces `parent.listId === listId`.
- `loadListPageData`, item `loadItemDetailData` (`page-data.ts:118-125`) and `exportListCsv` all verify URL `workspaceId` against the real List/Item Workspace and return `null`/404 for `NONE`.
- Viewer/Guest ceiling: every Item write requires `WRITE`; the Workspace Viewer cap in `resolveListAccess` (`:60-64`) downgrades any List role to `READ`. The only intentional exception is `upsertPersonalNote` (row 6 asks only for a `READ` floor).
- Workspace administration (`createInvitation`, `resendInvitation`, `revokeInvitation`) load the invitation's real Workspace and require Owner/Admin of a SHARED Workspace; `workspace-access.ts` helpers are used here.
- Auth-only user actions (`settings/security`, `settings/notifications`, `forgot/reset/verify`, `two-factor`) are scoped to `session.user.id`.

## Suggested remediation order (for the child issues under #80)

1. Central resolvers: add `Workspace.deletedAt` + `List.archivedAt` handling and the `ListMember`-requires-`WorkspaceMember` rule to `resolveListAccess`, and introduce `resolveWorkspaceAccess` to replace the raw compares in row 18 (rows 1, 8, 9, 18, 20-22). Depends on #75 landing the `deletedAt` column.
2. Close private-List leaks: assignee access validation, notification and My Tasks/Home read filters, Dependency title redaction (rows 2-5, 7).
3. Invitation acceptance email verification and the open redirect (rows 11, 12).
4. Integrity and ADR 0009 fidelity: Section ownership, last-Lead protection, Guest reachability and roster exposure (rows 10, 13-16).
5. Low-severity hardening (rows 17, 19, 23-25) and the Channel access-check helper for ADR 0013 (row 26).
