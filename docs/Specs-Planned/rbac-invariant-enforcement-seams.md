# RBAC Invariant Enforcement Seams

## Problem Statement

Two RBAC invariants have no settled enforcement seam, and a third problem is pure duplication risk. First, `resolveListAccess` trusts a `ListMember` row's role even when the User has no `WorkspaceMember` row at all in that Workspace — an orphaned `ListMember` silently grants access, and the only existing defense (cleanup-on-exit inside `removeWorkspaceMember`/`leaveWorkspace`) only prevents new orphans at those two mutations, not a bug anywhere else; the most recent commit on `main` at the time of writing is a data migration that had to repair exactly this kind of damage after the fact. Second, the never-empty-Lead rule is already correctly enforced at every current mutation that can remove or demote a Lead-bearing row, but this was never formally ratified as THE mechanism, leaving open whether a future change should instead reach for a DB constraint or trigger. Third, 5 call sites (`list-creation.ts`, `list-labels.ts`, `workspace-peer-comparison.ts`, `list-browsing.ts`, `global-search.ts`) each hand-roll their own Workspace-role check instead of calling a shared resolver, and 3 of those 5 don't check for a soft-deleted Workspace at all — a second, independent gap riding along with the duplication.

This was settled in the grilling session resolving [issue #86](https://github.com/codesuke/ListItUp/issues/86), recorded in `docs/QnA/rbac-invariant-enforcement-seams.md` and [ADR 0019](../ADR/0019-rbac-invariant-enforcement-seams.md). This spec implements that resolution.

## Solution

Add a defensive check inside `resolveListAccess` so a `ListMember`/`Guest` row never grants access without a live `WorkspaceMember` row backing it. Ratify the existing shared-locking-helper pattern as the never-empty-Lead rule's one enforcement mechanism, with no DB-level change, formalized by a doc comment. Build `resolveWorkspaceAccess`, a Workspace-level access-level resolver mirroring `resolveListAccess`'s shape, and route the 5 affected call sites through it (directly or through thin boolean wrappers kept for call-site readability), closing their missing deleted-Workspace handling as a side effect. Add a cross-check test pinning the hand-rolled visibility filters in `browseLists`/`globalSearch` against `resolveListAccess`'s per-row answer.

## User Stories

1. As a developer, I want `resolveListAccess` to return `NONE` whenever the User has no `WorkspaceMember` row in the List's Workspace, even if a `ListMember` or `Guest` row names them, so that an orphaned row (from a bug, a bypassed cleanup path, or data predating this fix) can never silently grant access.
2. As a developer, I want the existing cleanup-on-exit (`clearWorkspaceListAccess`) to keep running on `removeWorkspaceMember`/`leaveWorkspace`, so that orphaned rows don't accumulate just because they're now harmless.
3. As a developer reading `lib/list/list-membership.ts`, I want a doc comment on `lockAndCountSoleLeadLists`/`lockAndInspectListMember` stating that every mutation deleting or demoting a List-role or Workspace-role row that could be a List's last Lead must acquire this lock first, so that the never-empty-Lead rule's one sanctioned mechanism is discoverable rather than tribal knowledge.
4. As a developer, I want one `resolveWorkspaceAccess(database, {userId, workspaceId})` function returning a `WorkspaceAccessLevel` (`NONE`/`VIEWER`/`MEMBER`/`ADMIN`/`OWNER`), mirroring `ListAccessLevel`'s shape and resolution style, so that Workspace-level authorization has the same kind of single resolver List-level access already has.
5. As a developer, I want `resolveWorkspaceAccess` to return `NONE` for a soft-deleted Workspace regardless of the User's role, so that every caller gets deleted-Workspace handling for free instead of needing to remember it individually.
6. As a developer, I want `meetsWorkspaceAccessLevel(level, required)` mirroring `meetsListAccessLevel`, so that ceiling comparisons read the same way at every call site across both resolvers.
7. As a developer, I want `canManageWorkspace`, `canAccessWorkspaceSettings`, and `canViewWorkspaceMembers` to keep their existing names and signatures but be implemented in terms of the resolved `WorkspaceAccessLevel` internally, so that existing call sites don't need to change and there's exactly one place the role hierarchy and deleted-Workspace handling actually live.
8. As a developer, I want a new `hasImplicitListAccess(level)` predicate capturing the Owner-sees-every-List rule, so that `list-browsing.ts` and `global-search.ts` import the same named rule `resolveListAccess` encodes internally instead of each re-typing `role === "OWNER"`.
9. As a Workspace Owner or Admin creating a List, I want `createList`'s authorization check to route through `resolveWorkspaceAccess`/`canManageWorkspace`, so that it also correctly refuses while the Workspace is soft-deleted, which it doesn't check today.
10. As a Workspace Owner or Admin creating a Label, I want `createLabel`'s authorization check to route through the same resolver, for the same reason.
11. As a Workspace Owner or Admin toggling Peer Comparison, I want `setPeerComparisonEnabled`'s authorization check to route through the same resolver, for the same reason.
12. As any User browsing or searching Lists, I want `browseLists` and `globalSearch`'s "do I see every List" check to use `hasImplicitListAccess` instead of a hand-coded `role === "OWNER"` string compare, so the rule is named once.
13. As a developer, I want `list-roles.ts` left untouched, since its List-role filters are display grouping for the Roles tab, not a Workspace-role authorization check, and were only in the original audit by miscount.
14. As a developer, I want a regression test constructing a `ListMember` row for a User with no `WorkspaceMember` row in that Workspace, asserting `resolveListAccess` returns `NONE` for every `ListMember`/`Guest` role combination, so L1 is pinned and can't silently regress.
15. As a developer, I want a cross-check test asserting `browseLists` and `globalSearch`'s hand-rolled visibility OR-filters agree with `resolveListAccess`'s per-row `>= READ` answer across a representative matrix of Workspace role, List role, Guest, and no-relationship combinations, so a future change to `resolveListAccess`'s resolution order that isn't mirrored in these two filters fails a test instead of silently drifting.
16. As a developer, I want `resolveListAccess` itself left unchanged in its own Workspace-membership lookup (not refactored to call `resolveWorkspaceAccess` internally), since this spec's scope is the invariants above, not a rewrite of an already-shipped, heavily depended-on resolver.

## Implementation Decisions

- Add the `WorkspaceMember`-existence guard as the first check inside `resolveListAccess`, before the existing deleted-Workspace check or after it (either order is correct since both short-circuit to `NONE`) — a missing `WorkspaceMember` and a deleted Workspace both resolve to `NONE` for every role.
- `resolveWorkspaceAccess` lives in `lib/permissions/workspace-access.ts`, alongside the predicates it now backs. It queries the Workspace for `deletedAt` and the `WorkspaceMember` row for the given `userId`/`workspaceId`, returning `NONE` if either is absent/deleted, otherwise the membership's `role` cast directly to `WorkspaceAccessLevel` (the two types share their value set above `NONE`, so no translation table is needed beyond the `NONE` case).
- `meetsWorkspaceAccessLevel` follows `meetsListAccessLevel`'s exact shape: an ordered array (`NONE`, `VIEWER`, `MEMBER`, `ADMIN`, `OWNER`) and an index comparison.
- `canManageWorkspace`, `canAccessWorkspaceSettings`, and `canViewWorkspaceMembers` keep their current call signatures (they currently take a bare `role`, not `{userId, workspaceId}`) — only their internal implementation changes to route through the shared level-ordering logic; callers that already have a `WorkspaceRole` in hand (not every call site has a database handle available at the point of the check) are unaffected. Where a call site currently does its own `database.workspaceMember.findUnique` and then calls one of these predicates, it switches to calling `resolveWorkspaceAccess` once and passing the resolved level through.
- `hasImplicitListAccess(level: WorkspaceAccessLevel): boolean` returns `level === "OWNER"` — exact equality reads the same as a ceiling check here since `OWNER` is the top of the order, but equality is clearer given there's no "OWNER or above" tier.
- `list-creation.ts`'s `createList` and `list-labels.ts`'s `createLabel` switch from their local `ROLES_ALLOWED_TO_CREATE_LIST`/`ROLES_ALLOWED_TO_CREATE_LABEL` arrays to `resolveWorkspaceAccess` + `canManageWorkspace`, inside their existing transactions. `workspace-peer-comparison.ts`'s `setPeerComparisonEnabled` switches from its local `ALLOWED_ROLES` set the same way.
- `list-browsing.ts`'s `browseLists` and `global-search.ts`'s `globalSearch` switch their `canSeeEveryList = workspaceMembership?.role === "OWNER"` line to `canSeeEveryList = hasImplicitListAccess(resolvedLevel)`, reusing the Workspace-membership/deleted-Workspace lookup they already perform rather than adding a second query.
- Add a doc comment on `lockAndCountSoleLeadLists`/`lockAndInspectListMember` (`list-membership.ts`) stating they are the one sanctioned way to delete or demote a row that could be a List's last Lead, and that any new mutation touching `ListMember`/`WorkspaceMember` rows must acquire this lock first inside its own transaction — mirroring `resolveListAccess`'s own existing "every List-scoped check should call this" comment.
- No schema change. No DB trigger or constraint.

## Testing Decisions

- Add the L1 regression test (User Story 14) to `lib/permissions/list-access.test.ts` or its integration counterpart, matching the existing seam for that module.
- Add `resolveWorkspaceAccess`/`meetsWorkspaceAccessLevel`/`hasImplicitListAccess` unit tests in a new or extended `lib/permissions/workspace-access.test.ts`, covering every role, no-membership, and deleted-Workspace case — same style as `list-access.test.ts`'s coverage of `resolveListAccess`.
- Update `list-creation.test.ts`/`.integration.test.ts`, `list-labels.test.ts`/`.integration.test.ts`, and `workspace-peer-comparison.test.ts`/`.integration.test.ts` with a new case: the action is refused while the Workspace is soft-deleted, even for an Owner/Admin who'd otherwise be allowed — this is the deleted-Workspace gap being closed, and should fail against the current code before the fix lands.
- Add the cross-check test (User Story 15) as a new integration test alongside `list-browsing.integration.test.ts` and `global-search`'s existing integration test, iterating a representative combination matrix rather than exhaustive enumeration (Owner, Admin, Member-with-List-role, Member-without-List-role, Viewer-with-List-role, Guest, no-relationship — crossed with List-role Lead/Member/Viewer where applicable).
- No new structural/grep-based test for the never-empty-Lead guardrail, per the grilling session's decision — convention and the new doc comment are the chosen guard.

## Out of Scope

- Any DB constraint or trigger for the never-empty-Lead rule or L1 — explicitly rejected by the grilling session.
- Refactoring `resolveListAccess` to compose on `resolveWorkspaceAccess` internally — explicitly deferred.
- Any change to `list-roles.ts` — its role filters are not an authorization check.
- Any change to the existence or shape of the hand-rolled visibility OR-filters in `browseLists`/`globalSearch` beyond adding the cross-check test — they remain bulk, set-based queries by necessity.
- A full audit of every other possible raw role compare in the codebase beyond the 5 named here — this spec closes the specific gaps named by the #81 audit and this grilling session, not a repo-wide sweep.

## Further Notes

- The L1 fix and the `resolveWorkspaceAccess` build-out are independent of each other and can land as separate, independently-demoable tickets; the 3 deleted-Workspace-gap fixes (`createList`, `createLabel`, `setPeerComparisonEnabled`) naturally arrive bundled with the `resolveWorkspaceAccess` ticket since they're the same code change (switching to the new resolver), not a separate fix.
- The cross-check test (User Story 15) is the one piece of new test infrastructure this spec introduces beyond the usual per-mutation test extension — it's testing an invariant between two modules (`list-browsing.ts`/`global-search.ts` vs. `list-access.ts`) rather than one module's own behavior, so it may be worth its own test file rather than living inside either module's existing test file.
