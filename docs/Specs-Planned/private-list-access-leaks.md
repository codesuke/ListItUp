# Private-List Access Leaks: Write- and Read-Time Enforcement

## Problem Statement

A private List's access boundary is supposed to mean a User with no access to it can't see its content anywhere, but today several surfaces other than the List itself leak around that boundary. `addAssignee` never checks whether the *target* User has any access to the item's List — only the actor's access is checked — so any User with WRITE can assign an item to a User with zero access, and that item then surfaces directly in the target's My Tasks. Notification creation checks access for @mention recipients only, not for assignee-added/removed or state-change recipients; the read path for Notifications, the inbox, My Tasks, Home, and Items I've Assigned all filter purely by `recipientId`/`assigneeId`/`creatorId`, with no re-check of the viewer's *current* access — so access revoked after a valid assignment doesn't retroactively hide anything, and Notification titles (a live join to `Item.title`, not denormalized) keep showing the item's current title to a recipient who has since lost access. A cross-List `ItemDependency`'s `blocking`/`blockedBy` rendering shows the other item's title and `listId` with no check against the viewer's access to that other List, even though creating the dependency correctly required WRITE on both sides. Personal Notes have no List-access floor on either read or write — the write path checks only "is currently an assignee," which stops being a meaningful access proxy once stale assignee rows are kept rather than deleted (see below). Items I've Assigned doesn't even exclude a deleted Workspace, a gap My Tasks already closes.

This was settled in the grilling session resolving [issue #87](https://github.com/codesuke/ListItUp/issues/87), recorded in `docs/QnA/private-list-access-leaks.md` and [ADR 0021](../ADR/0021-private-list-access-leaks-write-and-read-time-enforcement.md). This spec implements that resolution, published to the issue tracker as [#107](https://github.com/codesuke/ListItUp/issues/107).

## Solution

Add a write-time access gate to `addAssignee` requiring the target User to resolve to at least `READ` on the item's List. Add a read-time re-check of the *viewer's* current access to Notifications/inbox, My Tasks, Home, and Items I've Assigned, so access revoked after the fact is caught even though the write-time gate above only covers new assignments. Revoked access hides the affected `ItemAssignee`/`Notification` rows via this read-time filter; neither is ever deleted as a side effect of access loss alone (full-departure cleanup from issue #82 is unaffected). Cross-List `ItemDependency` rendering checks the viewer's access to the *other* item's List and substitutes an opaque placeholder when absent. `getPersonalNote`/`upsertPersonalNote` both gain a `resolveItemAccess` READ floor, additive to the existing "is assignee" check on the write path. My Tasks, Home, and Items I've Assigned additionally filter out archived-List items via a dedicated condition, independent of `resolveListAccess` (per ADR 0018, archiving stays orthogonal to access level).

## User Stories

1. As a List Member with WRITE access, I want `addAssignee` to refuse assigning an Item to a User who has no access to the Item's List, so that I can't accidentally (or deliberately) expose a private Item to someone who shouldn't see it.
2. As a List Member, I want a User with only `READ` (a Viewer or Guest) to still be a valid assignment target, so that assignment can be used for visibility/FYI purposes even when the assignee can't act on the Item themselves.
3. As a User who has lost access to a List (removed as a Member, Guest access revoked, or role downgraded to Viewer where that matters), I want Items I'm still an `ItemAssignee` of on that List to disappear from My Tasks and Home, so that losing access actually means losing visibility, not just losing the ability to open the List directly.
4. As a User who has lost access to a List, I want Notifications and inbox entries about that List's Items to disappear, so that a Notification can't be used to keep reading an Item's current title and activity after access is revoked.
5. As a User whose access to a List is later restored (re-added as a Member, Guest re-granted), I want my previous assignments and Notifications about that List to reappear automatically, so that I don't have to be reassigned or re-notified from scratch.
6. As a User creator viewing Items I've Assigned, I want it to exclude Items in a List I (the viewer) no longer have access to, and to exclude Items in a deleted Workspace, matching My Tasks' existing deleted-Workspace handling.
7. As a User with `READ` access to an Item, I want a cross-List `blocking`/`blockedBy` dependency pointing at an Item in a List I don't have access to, to render as an opaque placeholder (e.g. "Blocked by an item you don't have access to") rather than showing that Item's real title, and rather than disappearing from the list entirely.
8. As a User, I want my own Personal Note on an Item to stop being readable or writable by me once I no longer have at least `READ` access to that Item's List, even if I still technically hold a stale `ItemAssignee` row.
9. As a User, I want archived-List Items to not appear in My Tasks, Home, or Items I've Assigned, even though I still have normal role-based access to that List, so that a frozen/closed List's Items don't clutter my active task queues.
10. As a developer, I want all of the above enforced through the existing `lib/permissions/` resolvers (`resolveListAccess`/`resolveItemAccess`), not a parallel ad hoc check, so this fix follows the same seam as every other access decision in the codebase.

## Implementation Decisions

- `lib/item/item-assignment.ts`: `addAssignee` calls `resolveItemAccess`/`resolveListAccess` against the target `userId` (in addition to the existing actor check) and returns a new discriminated-union case — e.g. `{ status: "assignee-no-access" }` — when the target resolves to `NONE`. `removeAssignee` is unaffected (removing access is always safe). The required level for the target is `READ`, not `WRITE` — a capped Viewer/Guest remains a valid assignee.
- `lib/notification/notification-inbox.ts`: each loader (`loadActivityNotifications`, `loadBookmarkedNotifications`, `loadArchivedNotifications`, `loadMentionedNotifications`, `countUnreadNotifications`) adds a per-row current-access check against the Notification's underlying Item/List (via `resolveItemAccess`, or a batched equivalent if an N+1 query would otherwise result — see Testing Decisions) before including a row in the result. No change to `notification-triggers.ts`'s creation-time behavior beyond what's already correct for mentions; the read-time check is the actual fix, not a creation-time one, since creation-time access can go stale.
- `lib/item/item-my-tasks.ts`: `loadMyTasksItems` adds the same current-access re-check per Item (the query already joins to `list`/`workspace`; extend the `where` or post-filter using `resolveListAccess`'s rules) and adds an `archivedAt: null` condition on the List.
- `lib/item/item-assigned-by-me.ts`: `loadAssignedByMeItems` adds the `ACTIVE_WORKSPACE_WHERE` condition it's currently missing, the same current-access re-check (this time for the *viewer*, who is the creator — a creator can lose List access the same way an assignee can), and the same `archivedAt: null` condition.
- `lib/item/item-dependencies.ts` / `page-data.ts`: `loadItemDetailData`'s `blocking`/`blockedBy` mapping resolves the viewer's access to each dependency's *other* item's List and substitutes a placeholder shape (e.g. `{ id, accessible: false }` in place of `{ id, title, listId }`) when access is below `READ`. The dependency row itself is still included — never dropped from the list — only its title/listId content is withheld.
- `lib/item/item-notes.ts`: `getPersonalNote` and `upsertPersonalNote` both call `resolveItemAccess` and require at least `READ`; `getPersonalNote` returns "not found" (not an error) when access is below `READ`, matching how a hidden row behaves elsewhere in this spec. `upsertPersonalNote` keeps its existing "is assignee" check as an additional, not replaced, condition.
- No schema change. No new Prisma model or migration — every fix here is a query/check addition to existing functions.
- Follow the existing per-module discriminated-union result pattern (e.g. `{ status: "forbidden" }`, `{ status: "list-not-found" }`) for every new rejection/empty case introduced above, rather than throwing or returning `null` inconsistently.

## Testing Decisions

- `item-assignment.integration.test.ts`: update the existing case that currently asserts assigning a User with zero access succeeds — it must now assert `{ status: "assignee-no-access" }` (or the chosen case name) and no `ItemAssignee` row created. Add a case confirming a Guest/Viewer-level target (`READ` only) is still accepted.
- `item-my-tasks.integration.test.ts` / `item-assigned-by-me.integration.test.ts`: add a case where a User is an assignee/creator on an Item whose List access they've since lost (List membership removed, or Guest access revoked) and assert the Item no longer appears; add a case where access is restored afterward and assert the Item reappears without re-assignment. Add a case for an archived List's Item being excluded regardless of normal access.
- `notification-inbox.integration.test.ts` (or equivalent): add a case asserting a Notification about an Item the recipient has since lost access to is excluded from every loader (`loadActivityNotifications`, etc.) and from the unread count, and reappears if access is restored.
- `item-dependencies.integration.test.ts` / the List item-detail page-data test: add a case where a `blocking`/`blockedBy` Item lives in a List the viewer can't access, asserting the placeholder shape is returned (not the real title, not an empty list).
- `item-notes.integration.test.ts`: add cases for `getPersonalNote` and `upsertPersonalNote` both refusing (not-found / rejected) once the caller's List access drops below `READ`, even while a stale `ItemAssignee` row for them still exists on the Item.
- If the read-time access re-check in any of the above would otherwise require one `resolveListAccess` call per row (N+1), batch it (e.g. resolve access once per distinct `listId` in the result set) and add a unit test asserting the batched helper's output matches `resolveListAccess` called individually per row, following the cross-check pattern already used for `browseLists`/`globalSearch` in `docs/Specs-Completed/rbac-invariant-enforcement-seams.md`.
- Follow each module's existing test seam (unit vs. integration) rather than introducing a new one.

## Out of Scope

- Issue #82's full-Workspace-departure cleanup (deleting assignments/Guest grants/invitations) — already decided and unaffected by this spec; this spec only covers access lost while the User remains in the Workspace.
- Any change to `resolveListAccess`'s resolution rules or to ADR 0018's archived-List-is-orthogonal decision — the archived-List filter here is a dedicated, separate condition in the three task-queue surfaces, not a change to the resolver.
- A general "placeholder item" concept beyond the cross-List dependency rendering case — no other surface in this spec needs one.
- UI copy/visual design for the opaque placeholder beyond "shows that something exists without revealing its content" — exact wording is an implementation detail for whoever builds this slice.
- Any change to how @mention notifications already check access at creation time — already correct, untouched.

## Further Notes

- This spec's fixes are independent enough (five separate modules: assignment, notifications, My Tasks, Items I've Assigned, dependencies, notes) that when broken into tickets via `to-issues`, each module is its own independently demoable vertical slice rather than one large ticket.
- The read-time re-check added here is the first place several of these modules call `resolveListAccess`/`resolveItemAccess` per result row rather than per single target; watch for N+1 query cost and batch per the Testing Decisions note above.
